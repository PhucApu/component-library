The change is shown before it is saved

A reorder has to feel instant, so the row lands where it was dropped and the request goes out afterwards. That is a promise the component then has to keep — and something has to undo it honestly when the server says no.

What a refusal has to do

Switch to Saving fails and move a row. The list holds at reduced opacity while the request is out, then the row goes back to exactly where it started and the reason is announced — not a silent revert, and not a toast pointing at a list that has already changed underneath it.

Two reorders in flight

Each request carries a token. Without one, a slow failure could roll back a change the reader has since replaced — the list would jump to an order nobody chose. Only the newest request is allowed to touch the rows.

The same contract as the switch

commit takes an async function and receives { from, to, order }. Reject it to refuse. It is deliberately the shape ui-switch already uses in this collection, because it is the same problem: an optimistic change that something has to be able to take back.
